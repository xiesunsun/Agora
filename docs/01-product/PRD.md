# Agent 文本黑板会话 PRD

## 1. 产品概述

### 1.1 产品名称

**Agent Text Blackboard**
中文名：**Agent 文本黑板会话**

### 1.2 产品定位

Agent 文本黑板会话是一个面向 Human-in-the-loop Agent 协作的轻量文本讨论空间。

Agent 通过 Skill 与 CLI 创建并管理黑板会话。人类通过 Agent 自动打开的 HTML 页面参与讨论、编辑、批注、审阅和推进。双方围绕同一份文本持续协作，使文本在一轮轮讨论中形成清晰、可追踪、可审阅的版本演进。

### 1.3 产品目标

产品目标是让人类在一个专注的文本现场中与 Agent 共同推进复杂问题，而不是通过零散聊天来补充上下文。

黑板会话需要支持以下核心体验：

1. 人类在网页中直接表达想法，包括编辑正文、添加批注。
2. Agent 在后台持续跟随人类的修改和批注，形成对当前讨论方向的理解。
3. 人类通过 **Proceed** 明确切换回合，让 Agent 将本轮理解落实为文本修改。
4. Agent 的回应直接发生在黑板页面中，先形成待审阅改动，并在审阅接受后形成新版本与必要 diff。
5. 人类始终拥有最终控制权，可以继续修改、批注、审阅或结束会话。

## 2. 核心用户与使用场景

### 2.1 核心用户

本产品面向需要与 Agent 共同打磨复杂文本内容的用户。

典型用户包括：

| 用户类型               | 使用诉求                       |
| ------------------ | -------------------------- |
| 产品设计者              | 与 Agent 共同打磨产品定义、PRD、交互流程  |
| 开发者 / 技术负责人        | 审阅 Agent 生成的技术方案、实现计划、接口契约 |
| 内容创作者              | 与 Agent 共同修改文章、脚本、长文结构     |
| Prompt / Agent 设计者 | 迭代提示词、Agent 行为规则、任务流程      |
| 研究型用户              | 梳理问题、比较方案、沉淀分析结论           |

### 2.2 典型场景

#### 场景一：产品定义讨论

用户希望和 Agent 共同整理一个新产品的定义。
Agent 创建黑板并生成初始结构。用户在页面中修改不准确的表达，批注产品体验上的问题。点击 Proceed 后，Agent 根据本轮反馈局部改写文本并进入审阅；若审阅接受，则形成新版本。

#### 场景二：技术方案审阅

Agent 写出一份实现计划。用户在关键段落添加批注，指出风险、约束和遗漏。点击 Proceed 后，Agent 修正方案。对于关键改动，用户进入高级审阅模式，逐 hunk 接受或拒绝。

#### 场景三：Prompt 模板迭代

用户和 Agent 共同打磨一份提示词模板。用户直接修改措辞，对部分规则进行批注。Agent 跟随这些修改，并在 Proceed 后提交待审阅改动；若审阅接受，则形成更稳定、更可执行的新版本。

#### 场景四：文章结构共创

Agent 生成文章初稿。用户在页面中调整段落顺序、重写部分内容，并对不满意的段落添加批注。Agent 在下一轮中局部润色并整理结构，使文章逐步收敛。

## 3. 产品核心概念

### 3.1 黑板会话

黑板会话是一次由 Agent 创建、由人类在网页中参与、围绕一份文本持续推进的协作过程。

一个黑板会话包含：

* 当前文本内容；
* 人类编辑记录；
* 人类批注；
* Agent 后台跟随状态；
* Proceed 回合记录；
* Agent 修改版本；
* diff；
* 会话结束总结。

### 3.2 正文编辑

正文编辑是人类对文本内容的直接修改。

正文编辑代表人类已经做出明确判断。Agent 在后续修改中应优先保留人类直接编辑过的内容，除非人类后续批注明确要求重新处理。

### 3.3 批注

批注是人类针对具体文本片段提出的讨论性意见。

批注用于表达：

* 这段不准确；
* 这里需要换一种角度；
* 这个概念需要收敛；
* 这个表达需要更清楚；
* 这个地方需要 Agent 注意并回应。

批注是 Agent 在 Proceed 后需要处理的重要输入。

### 3.4 Proceed

Proceed 是黑板会话中的回合切换操作。

人类点击 Proceed 表示：

> 本轮表达已经完成，请 Agent 基于当前正文和批注提交回应与修改。

Proceed 触发 Agent 将后台理解落实为一次可见的待审阅改动更新。

### 3.5 版本

版本是 Agent 的待审阅改动在审阅接受后形成的正式文本状态。

每个版本包含：

* 版本编号；
* 完整正文；
* 必要的历史元数据。

### 3.6 Diff

Diff 用于展示 Agent 在本轮中对文本做出的具体修改。

Diff 需要帮助人类快速理解：

* 删除了什么；
* 新增了什么；
* 改写了什么；
* 改动集中在哪些区域。

### 3.7 高级审阅模式

高级审阅模式用于严肃文本场景。

在该模式下，Agent 的修改以 proposed changes 形式呈现。页面按语义 hunk 展示改动，人类可以逐 hunk 执行：

* Accept：接受改动；
* Reject：拒绝改动。

## 4. 产品形态

### 4.1 Agent 侧入口

Agent 使用 **Skill + CLI** 操作黑板。

在 V1 中，更准确的运行形态是：

* `main agent` 负责总任务编排；
* `main agent` 将需要进入可视化协作的内容交给专用 `subagent`；
* 当前黑板会话由该 `subagent` 在自己的上下文中持续托管；
* 会话关闭后的结果与总结再回传给 `main agent`。

Skill 负责定义 Agent 的使用规则：

* 何时打开黑板；
* 如何初始化黑板；
* 如何理解人类编辑与批注；
* Proceed 后如何回应；
* 如何提交版本；
* 如何在关闭后总结。

CLI 负责提供 Agent 可调用的正式工具能力：

* 创建黑板会话；
* 主动读取当前会话快照；
* 标记某条 bullet 已完成局部处理；
* 提交 Agent 生成的整篇候选正文；
* 结束会话并返回总结上下文。

说明：

* V1 的主工作模式是 `command + event stream`；
* `subagent` 不通过显式 `await_event` 命令轮询事件，而是由运行时将会话事件桥接进当前 Agent 长会话；
* `subagent` 的本地工作区可以保存草稿、局部处理结果与统合计划；
* 黑板业务状态真相仍由 backend 持有，而不由 Agent 本地文件直接承载。

### 4.2 人类侧入口

人类通过 Agent 自动打开的 HTML 页面参与黑板会话。

HTML 页面需要提供：

* 文本阅读区域；
* Markdown 编辑能力；
* 选区批注能力；
* Agent 小人状态区；
* Proceed 操作；
* 版本历史；
* 高级审阅模式；
* 关闭会话入口。

### 4.3 注意力设计

黑板页面是人类参与讨论的主界面。

会话打开后，人类主要在 HTML 页面中完成阅读、修改、批注、审阅和推进。Agent 的中间回应也应呈现在黑板页面中，保持协作现场的一致性。

## 5. 标准用户流程

### 5.1 创建会话

1. 人类在聊天中提出需要共同讨论的问题。
2. 人类表达打开黑板的意图。
3. Agent 调用 CLI 创建黑板会话。
4. Agent 生成或导入初始文本。
5. 系统自动打开 HTML 页面。
6. 人类进入黑板页面。

### 5.2 人类表达

人类在黑板页面中进行本轮表达，包括：

* 直接修改正文；
* 删除不合适内容；
* 补充新内容；
* 选中文本添加批注；
* 查看 Agent 小人状态。

Agent 在后台持续接收并理解这些操作。

### 5.3 Agent 后台跟随

Agent 在后台跟随本轮变化，并形成对以下内容的理解：

* 人类修改了哪些内容；
* 哪些修改代表明确决定；
* 哪些批注需要回应；
* 哪些批注指向相同问题；
* 哪些部分需要局部改写；
* 哪些内容应保持不变；
* 本轮整体方向是什么。

该阶段 Agent 不直接修改正文。

### 5.4 人类点击 Proceed

人类点击 Proceed 后，系统进入 Agent 回应阶段。

此时：

1. 页面进入处理中状态。
2. Agent 小人切换到 working 动画。
3. 人类本轮输入被锁定，避免与 Agent 修改冲突。
4. Agent 基于本轮输入生成待审阅改动集。
5. 页面进入审阅阶段。

### 5.5 Agent 提交待审阅结果

Agent 完成处理后，页面展示：

* 待审阅正文；
* 修改区域高亮；
* 审阅入口；
* diff / hunk 视图；
* 本轮处理结果。

人类完成审阅后，系统才会决定生成新版本或回到 Proceed 前现场。

### 5.6 默认审阅流程

默认模式为 Flow Review。

流程如下：

1. Agent 生成一份整篇可审阅的候选改动。
2. 页面以 inline tracked changes 形式展示整篇正文。
3. 人类可执行 Accept All Remaining 或 Reject All Remaining。
4. 人类也可以切到 PR Review 逐项审阅。
5. 至少存在一个接受项时生成新版本；若全部拒绝则回到 Proceed 前现场。

该模式优先保证讨论流畅性。

### 5.7 高级审阅流程

用户开启高级审阅模式后，Proceed 后进入 PR Review。

流程如下：

1. Agent 生成 proposed changes。
2. 页面按语义 hunk 展示改动。
3. 人类逐 hunk 选择 Accept 或 Reject。
4. Accept 的 hunk 进入最终结果。
5. Reject 的 hunk 保留原文。
6. 人类可切回 Flow Review 查看整篇结果。
7. 若最终至少存在一个接受项，则生成正式版本；若全部拒绝，则不生成新版本。

该模式优先保证精确控制权。

### 5.8 关闭会话

人类关闭黑板时，系统结束当前会话。

关闭后，Agent 在聊天窗口中给出总结：

* 最终版本内容；
* 相比初始版本的主要变化；
* 讨论中形成的关键共识；
* 仍未解决的问题；
* 根据原始任务给出的下一步建议。

## 6. 核心交互规则

### 6.1 人类主导节奏

人类决定何时 Proceed，何时继续修改，何时结束会话。

Agent 不主动推进回合。

### 6.2 Agent 前台克制，后台主动

Agent 在后台持续跟随和理解人类输入。

Agent 不在 Proceed 前修改正文，不通过聊天打断人类当前流程。

### 6.3 正文编辑优先保留

人类直接编辑正文代表明确决定。

Agent 后续修改应避免覆盖人类编辑，除非人类批注明确要求调整。

### 6.4 批注必须回应

Proceed 后，Agent 需要处理本轮批注。

处理方式可以包括：

* 采纳并修改文本；
* 部分采纳；
* 不采纳但说明原因；
* 将批注转化为下一轮待讨论问题。

### 6.5 局部修改优先

Agent 修改应尽量匹配人类反馈的语义范围。

精准批注对应精准修改。
局部问题对应局部改写。

### 6.6 会话关闭后必须形成总结

V1 中，主要总结义务发生在会话关闭后，而不是每个版本落版时。

会话关闭后，`subagent` 必须向 `main agent` 回传本次黑板协作的整体结果，包括做了什么修改、达成了什么结论、以及仍未解决的问题。

### 6.7 Diff 必须可查看

每个 Agent 生成版本都必须支持 diff 查看。

Diff 是建立信任和控制感的基础能力。

## 7. Agent 小人体验

### 7.1 设计目标

Agent 小人用于表达 Agent 的在场感、跟随感和回应节奏。

它不是功能按钮，也不是系统通知。

它是黑板会话的情绪锚点，让人类感觉 Agent 正在旁边听、记、想，并等待合适时机回应。

### 7.2 基础状态

Agent 小人至少支持以下状态：

| 状态        | 含义    | 表现        |
| --------- | ----- | --------- |
| listening | 正在跟随  | 看向文本，轻微点头 |
| noting    | 正在记录  | 拿小本本写字    |
| thinking  | 正在思考  | 托腮、翻看笔记   |
| puzzled   | 存在不确定 | 歪头、停笔     |
| ready     | 准备回应  | 合上本子、抬头   |
| working   | 正在修改  | 快速写字或整理纸张 |

### 7.3 展示原则

Agent 小人应保持轻量、安静、陪伴式。

它不应频繁弹出文字提示，不应遮挡正文，不应抢夺人类注意力。

## 8. 版本与审阅

### 8.1 版本列表

页面应提供版本列表。

每个版本展示：

* 版本号；
* 创建时间；
* 恢复入口。

### 8.2 Diff 视图

Diff 视图展示当前版本相对上一版本的变化。

Diff 应支持：

* 新增内容；
* 删除内容；
* 改写内容；
* 修改区域定位。

### 8.3 Flow Review

Flow Review 是默认模式。

特点：

* Agent 修改先形成整篇待审阅候选结果；
* 人类通过整篇高亮理解变化；
* 人类可整体接受或整体拒绝剩余改动；
* 适合快速推进。

### 8.4 PR Review

PR Review 是高级审阅模式。

特点：

* Agent 修改先形成 proposed changes；
* 改动按 hunk 展示；
* 人类逐 hunk Accept 或 Reject；
* 只有被接受的 hunk 进入正式版本；
* 适合重要文本。

## 9. MVP 范围

### 9.1 MVP 必须支持

| 模块          | 能力                 |
| ----------- | ------------------ |
| Agent 入口    | Skill + CLI 打开黑板   |
| 页面打开        | Agent 自动打开 HTML 页面 |
| 文本主体        | Markdown 文本展示与编辑   |
| 批注          | 选区行内批注             |
| 后台跟随        | Agent 接收并理解人类修改和批注 |
| Agent 小人    | 展示 Agent 跟随状态      |
| Proceed     | 人类触发 Agent 回应      |
| Agent 修改    | Proceed 后生成待审阅改动集 |
| 版本          | 审阅接受后生成新版本        |
| Diff        | 展示版本间变化            |
| Flow Review | 默认审阅模式             |
| PR Review   | 高级 hunk 审阅模式       |
| 关闭总结        | 关闭黑板后 Agent 总结     |

### 9.2 MVP 边界

MVP 仅支持单人类与单 Agent 的文本协作。

MVP 文本格式以 Markdown 为主。

MVP 以本地或单用户会话为优先形态。

MVP 的目标是验证：

> 人类是否愿意停留在网页文本黑板中，通过编辑、批注和 Proceed 与 Agent 持续共同推进文本。

## 10. 成功标准

### 10.1 核心体验成功标准

产品应满足以下标准：

1. 用户打开黑板后，可以在网页中完成主要协作流程。
2. 用户不需要频繁回到聊天窗口补充上下文。
3. Agent 能准确理解人类直接修改与批注之间的语义差异。
4. Proceed 后 Agent 的修改能回应本轮主要反馈。
5. Agent 的修改范围符合用户反馈范围。
6. 用户能够通过待审阅改动、最终文本和必要 diff 理解 Agent 做了什么。
7. 用户能通过下一轮编辑、批注或 PR Review 纠正 Agent 的误解。
8. 关闭黑板后，Agent 能准确总结最终结果和讨论变化。

### 10.2 可用性验收标准

一次标准会话应能顺畅完成：

1. Agent 打开黑板。
2. 页面展示初始文本。
3. 用户编辑一段正文。
4. 用户对另一段添加批注。
5. 用户点击 Proceed。
6. Agent 生成待审阅改动集。
7. 用户在 Flow Review 或 PR Review 中处理改动。
8. 若存在 accepted change，系统生成新版本。
9. 用户关闭黑板。
10. Agent 输出会话总结。

### 10.3 质量标准

Agent 输出的新版本应满足：

* 保留人类直接编辑；
* 回应主要批注；
* 避免无关改写；
* 修改范围可解释；
* diff 清晰；
* 可继续迭代。

## 11. 核心原则

### 11.1 文本现场优先

所有关键协作行为尽量发生在黑板网页中。

### 11.2 人类控制优先

人类决定节奏、方向和最终版本。

### 11.3 Agent 克制回应

Agent 在后台积极跟随，在前台等待 Proceed 后回应。

### 11.4 局部修改优先

Agent 不以整篇重写作为默认回应方式。

### 11.5 版本可追踪

每轮 Agent 修改都形成可回看的版本记录。

### 11.6 Diff 可理解

Agent 修改必须让人类看得懂、追得上、改得回来。

### 11.7 审阅可升级

普通讨论使用 Flow Review；严肃文本使用 PR Review。

---

## 12. 文档结论

Agent 文本黑板会话的核心价值是提供一个真正适合 Human-in-the-loop Agent 协作的文本现场。

在这个现场中，人类不只是向 Agent 追加提示词，而是直接参与文本本身的演进；Agent 不只是一次性回答，而是在后台持续跟随人类的思路，并在 Proceed 后将理解落实为可审阅的新版本。

产品的第一阶段应聚焦于一个完整闭环：

> Agent 打开黑板
> → 人类在网页中编辑与批注
> → Agent 后台跟随
> → 人类点击 Proceed
> → Agent 生成待审阅改动集
> → 人类进行 Flow Review 或 PR Review
> → 审阅结算后决定是否生成新版本
> → 循环推进
> → 人类关闭黑板
> → Agent 总结结果

该闭环成立后，产品即可作为 Agent 协作中的通用文本 Human-in-the-loop 层。
